# Seth Event Recorder — High-Resolution Evidence Specification V1

> **Proposed implementation, not present in current ESP firmware.** User-requested "super high rate" must mean the **fastest verified reliable sampling of appropriate ECU sources**, not arbitrary ESP polling that starves engine communication. Passive capture and guided explanations only. No engine start, throttle, actuator, spark, load or dyno commands are generated by the recorder.

## The problem we're solving

When a user says `it briefly stumbled` or `it will crank but only occasionally fire`, an averaged gauge frame captured seconds afterward has missed the evidence. Seth needs a **before / during / after** trace with sensor and ECU-state context, and a traceability chain identifying each reading's source, units, actual acquisition time, trustworthiness and active calibration revision.

A capture from ordinary output-channel snapshots does **not** contain crank tooth timestamps. Trigger/phase debugging needs the ECU's special logger/sniffer stream when supported. A sensor report sampled at 100 Hz is not equivalent to the same sensor sampled natively at 10 kHz; never invent information between samples.

## Three recorder channels (orthogonal clocks)

1. **Ordinary ECU output-channel capture:** verified matched-INI fields, block reads, actual read cadence, and per-query start/end timestamps. Existing `telemetry.c` requests 10/20/50/100 Hz and holds shared snapshots while a client is subscribed. Move the recorder into a dedicated producer/consumer path, prioritizing safety and TunerStudio. Treat these as *requested targets* only. The ECU output block may take multiple 1024-byte USB reads; record intra-block skew.
2. **Special ECU diagnostics when supported:** trigger tooth/cam phase recorder, console-diagnostic event, ECU SD/NAND log or knock acquisition made available by the specific ECU firmware. Track its separate timestamp clock, sampling rate, buffer/loss counters and permissions. No attempt to imitate a waveform by repeating the latest output-channel value.
3. **Optional external context:** dedicated time-synchronized data logger, supported IMU, dyno evidence, technician-confirmed observation or environmental conditions; tag as independently measured, user-reported, derived or missing, and account for time-sync error. A phone or 3DS IMU is not a calibrated torque sensor.

## Recorder pipeline

```
 USB acquisition / ECU event source
       -> per-source bounded queue (nonblocking)
       -> raw bytes + INI/layout ID + timing record
       -> decoded role snapshot (with unit/source metadata)
       -> rolling PRE-EVENT buffer
       -> event trigger (rule or human "mark moment")
       -> POST-EVENT bounded capture and state classification
       -> evidence integrity check and immutable case bundle
       -> reasoner (offline or lower priority task)
       -> compact phone summary + on-demand trace + export
```

The continuous recorder owns a small circular in-memory cache. A **retention** policy and available hardware budget determine size. Do not assume PSRAM, external SPI SD, or onboard NAND is available merely because an ECU supports those options. Write large snapshots only where measured storage and power-loss handling are adequate. If no external storage exists, retain bounded summaries and report which raw data could not be saved.

## Recorder states

`OFF -> MONITORING -> ARMED -> CAPTURING -> FINALIZING -> READY -> REVIEWED`. Failure transitions to `PARTIAL`, `REJECTED`, or `SUSPENDED` with exact reason. `ARMED` means recording is prepared; it does **not** arm or control an engine.

- **MONITORING:** opt-in passive state observations within memory budget.
- **ARMED:** case intent, selected semantic roles, capture policy, time and storage bounds, quality requirements, valid source permissions; no actuator commands.
- **CAPTURING:** mark an event by user input or ECU-reported state transition/error-counter change; retain pre-event context and collect bounded post-event context automatically.
- **FINALIZING:** verify monotonic sequence/timing, annotate missing/split blocks, decode with exact INI, freeze a digest of calibration revision and record data completeness.
- **READY:** case visible to phone; high-rate samples need not be streamed to the phone at high rate.
- **PARTIAL:** a USB interruption, missing block, overrun or sensor invalidity cannot be silently patched; retain partial trace with explicit coverage.
- **REVIEWED:** reasoning and user review live as append-only annotations, not edits to raw samples.

## Capture profiles and eligibility

| Profile | Recommended evidence *sources* | Event marker (passive) | Validity / interpretation |
| --- | --- | --- | --- |
| ECU identity and reconnection | signature, firmware definition, USB readiness, configuration revision | connection state change | no engine inference on mismatched INI |
| Intermittent starting complaint | reported engine/cranking state, RPM, trigger/sync errors, battery, temperature, relevant fuel/spark requests, ECU faults | observed state transition or user-marked event | wideband may not be ready; ECU-reported requests do not prove physical actuation |
| Unexpected stall/after-start | previous and current RPM, status flags, idle target/command, relevant corrections | state transition to not running | distinguish stall onset from delayed consequences |
| Idle variation | ECU idle-active flag, target/actual RPM, idle actuator request, spark correction, MAP, lambda validity, trims | qualified repeated idle variation in reported data | idle actuator phase may lag RPM; correlation does not imply cause |
| Thermal difference | CLT/IAT, startup/correction state, battery, sensor readiness | ordinary session across existing temperature changes | separate events by verified environmental context |
| Steady fuel/trim discrepancy | target/measured lambda, bank-specific trim states, Gego with verified scale, fuel pressure where available, active enrichment | persistent qualified residual | no VE learning during unknown transients or active feedback masking |
| Transient observation | TPS/MAP/RPM, ECU engine flags, enrichment state, lambda, time alignment | reported state transition | account for transport/exhaust delay; not a steady VE sample |
| Trigger sync fault | specialized ECU tooth/edge capture **plus** output-channel context | ECU-reported sync/error event | ordinary 100 Hz logging cannot resolve missing teeth |
| Protection / sensor fault | ECU-reported fault bits, involved channels, config revision | new diagnostic condition | immediate explanation priority; no tuning proposal |
| External instrumented validation | matched dyno/pressure or professional measurement with sync metadata | externally recorded event | not automatically initiated by BrickOS |

**No instruction to recreate hazardous conditions.** Captures are from existing events or qualified supervision. If the event would require exposing people or equipment to risk to reproduce, Seth asks for a technician's evidence rather than initiating a procedure.

## Timing and synchronization

- **ESP monotonic time** stamps request issue, response receipt, decode and buffer insertion. Never rely on a phone wall clock as the event's primary time base.
- **ECU timestamps** are used only when the firmware exposes them and their clock mapping is verified. A single USB block may represent measurements generated at different internal times.
- **Per-source time envelope**: `earliest_possible_capture`, `latest_possible_capture`, `clock_uncertainty`, and `duration_ms`; events are aligned with **intervals**, not fabricated exact instants.
- **Lambda path delay** includes sensor/controller/exhaust transport; configurable per strategy and operating state, with a documented uncertainty. Never compare the current lambda frame to a current fuel command as if instantaneous.
- **Cross-source sync** is validated and recorded. If the IMU/dyno/event clock is not aligned, only broad, non-causal qualitative comparison is permitted.
- **Derivative estimates** need minimum sampling regularity, missing-sample guards and a noise budget; do not derive precise sensor response timing from irregular 100 Hz messages.

## Resource and throughput budget

`bytes_per_second = delivered_frames_per_second × complete_frame_bytes + metadata`. For example, a **hypothetical** 512-byte raw frame at 100 Hz requires ~51.2 kB/s before metadata; thirty seconds would be ~1.54 MB, beyond what may be viable in small internal RAM without external PSRAM. This is a sizing example **not a measured BrickOS benchmark**.

Compute budgets at compile and runtime from:
- verified free internal RAM and optional PSRAM,
- eligible storage and write bandwidth,
- current USB RTT/disconnect distribution,
- current ECU output block length,
- actual delivered sample rate and sample duration,
- relative priority of TunerStudio traffic and ECU communications,
- total active case count and retention policy.

Preferred approach: **compact, selected-role rings** for pre-event history and optional bounded raw-frame bursts when resources permit. Never cut unrelated ECU traffic priority to achieve an advertised "1000 Hz" capture. Phone display may update slowly while ESP holds full local evidence. On overflow, preserve fault/event markers and coverage metadata; drop lowest-priority display/optional samples first and mark the raw trace `partial`.

## API contract (proposed, not deployed)

- `GET /api/guide/v1/capture/capabilities` lists actual ECU source/role support, measured sustained rate bands, memory/store limits, and unsupported special sources.
- `POST /api/guide/v1/cases` creates a read-only diagnosis case bound to the ECU/INI/config revision.
- `POST /api/guide/v1/capture/arm` requests a bounded passive capture profile; authenticated user permission and resource validation required. It does **not** affect ECU run state.
- `POST /api/guide/v1/capture/mark` annotates an already occurring observation, with requester timestamp and uncertainty.
- `POST /api/guide/v1/capture/stop` stops this recording only, never stops or changes the engine.
- `GET /api/guide/v1/cases/{id}` returns state, onset/recovery summary, missing data, source links and portable Seth dialogue.
- `GET /api/guide/v1/cases/{id}/trace?cursor=...` paginates data in bounded chunks.
- `GET /api/guide/v1/cases/{id}/export` produces a self-describing evidence bundle with INI fingerprint and sensor units.
- `GET /api/guide/v1/status` returns queue, recorder overruns, CPU/storage budgets, observed USB data rate, faults and current case state.

Routes are distinct from existing `/api/live` and **do not modify or replace existing DS/TunerStudio endpoints**. Do not expose automatic ECU writes through these paths. The current open Wi-Fi AP is not a trusted authorization system; future controlled actions require independent secure pairing, and any write-capable operations require separate review.

## Data integrity / privacy

- Raw records are immutable once a case finalizes; annotations append separately.
- Every case has a configuration revision; a manual setting change starts a new comparison epoch.
- Retention and export are opt-in; keep identifiable log content on the device unless explicitly exported.
- Case history must survive a browser refresh when storage is available, but absence of persistent storage cannot be hidden.
- External technician input is labeled `user_reported` unless independently verified; optional uploaded logs carry a provenance record.
- Explain if a captured source lacked the relevant channel or if a sensor did not respond during the event.

## Test-driven release gates

1. **Bench transport stress:** fixed synthetic telemetry replay at various delivered rates, injected USB latency, timeouts, multi-chunk blocks, contention with normal manual/TunerStudio requests, and optional 3DS polling.
2. **Clock and quality tests:** source clock changes, missing frames, duplicated sequences, stale lambda, queue overrun, hardware reset, integer wrap, invalid scales and out-of-order packets.
3. **Resource tests:** no PSRAM, constrained internal RAM, storage full/unavailable and power interruption; no corrupted existing calibration or lockups.
4. **Event classification:** multiple events in one window, transient versus steady, false trigger and incomplete pre-event history; all retain reasons and do not fabricate causal order.
5. **Reader portability:** phone receives compact case summaries; future DS receives same case IDs and text-only fallback. Neither display owns the high-rate acquisition schedule.
6. **No-action test:** arming, marking, reading, exporting and ending cases never emit calibration write/burn, ECU start, output override or spark/boost command.
7. **Hardware validation:** measure real sustained rate and timestamp uncertainty on the actual target ESP32-S3/ECU, including native USB and ECU scheduling effects, before advertising any numeric capture rate.
